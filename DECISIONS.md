A coordinator is accountable, swappable, and never load-bearing; naming it after a magistrate who oversees the sovereign inverted the thing the whole `coordinator/CONTRACT.md` posture exists to guarantee. **A pier is infrastructure that serves vessels it does not own.** Many independent piers exist; you use whichever one you reach, and you leave — no migration, no re-keying, no residue. That is the contract, said in one word, and it completes the family: **kotva** (anchor) → **pier** → **depot**. Consequences settled with the rename: (a) **crates are namespaced `pier-*`**; (b) **this repo publishes nothing to crates.io** — `kotva` is the published home for anything third parties consume, and `scripts/check-no-publish.sh` enforces it (`OK: 15 crates, none publishable; workspace default is publish = false; no publish automation`); (c) **the console's operator branding is swappable**, so a third-party deployment is never mistaken for a VulOS-operated one — this repo is *published by* VulOS but is **not a VulOS product and not a VulOS-operated service**. What did NOT change, deliberately: the positioning — Pier is **the broker (coordinator) reference implementation of the KOTVA standard** — and every wire identifier, env var, CLI flag, binary name (`vulos-relayd`, `vulos-relay-agent`), Fly app name, container name and image tag, none of which ever carried the old name. The Go module path DID move, from the old-name path to `github.com/vul-os/pier`, and every import with it; `go build ./...`, `go vet ./tunnel/... ./cmd/...` and `go test ./tunnel/... ./cmd/...` (14 packages `ok`) are green after it. Supersedes `[2026-07-23 name]`.

The prose now points at those constants instead of restating the literal. The historical fact is preserved; the false claim is not created.
- `[2026-08-06 client-vs-console]` **`client/` is Svelte-free React-optional; `console/` is React-free Svelte. Two different frameworks because they are two different kinds of thing, not an inconsistency.** `client/` (`pier-client`) is a **publishable npm SDK** — `"private": false`, ships `dist-lib` with `main`/`module`/`types`/`exports`, and declares `react` as an *optional* `peerDependency` (`peerDependenciesMeta.react.optional`) purely so host apps that already run React can bind it without a second copy in their bundle; the SDK's own logic carries no UI framework requirement. `console/` (`pier-console`, added `17411c3`, "Harbor Ledger") is a **standalone internal operator console** for running a Wakala/pier coordinator — `"private": true`, never published, its own audience (operators, not third-party integrators) and its own lifecycle (ships and versions with this repo, not on a package registry). It was built in Svelte 5 on its own merits (small op-console surface, no need to match a consuming app's framework) with no obligation to match `client/`'s optional peer dep, because nothing ever imports `console/` as a library. Package managers follow the same split: `client/` uses npm (`package-lock.json`) as the plain, unsurprising default for a package meant to be `npm install`ed by external consumers; `console/` uses pnpm (`pnpm-lock.yaml`) as an internal app with no external installers to keep unsurprising for. Not a fleet-wide package-manager stance — just each app matching its own audience. (No prior written rationale existed for either choice before this entry; the only trace was `17411c3`'s commit message, which explains what console does but not why Svelte/pnpm over React/npm.)
